# Local application contract

Implementation contract for the 0.2.0 source, updated October 2, 2026. User-confirmed: all dashboard capabilities together, forwarding continues during recording pressure, hundreds of requests per second. Working defaults: Linux first, mixed workloads, full state opt-in, 7-day detailed retention with an adjustable record cap, 500 requests/s sustained and 1,000 requests/s burst test points. These are implementation choices and targets, not measured claims.

## Modules and boundaries

- `src/model.rs`: captured wire data, normalization, deterministic grouping, privacy, sample fixtures, import conversion.
- `src/store.rs`: SQLite migrations, batched writes, dashboard/detail queries, export, labels and deletion.
- `src/collector.rs`: bounded capture reservations and a single background normalization/database writer, independent health counters.
- `src/server.rs`: HTTP route composition and shared error responses. `src/server/` separates state construction, local access guards, shutdown, proxy/capture ownership, local API handlers and bundled UI assets. Proxy capture and response deadlines stay together; blocking database tasks retain their admission permits through cancellation.
- `src/config.rs`, `src/main.rs`: CLI validation and application startup.
- `ui/`: React + Vite browser app with local assets and Taste Skill visual guidance. No remote UI resources.

The module boundary uses `serde_json::Value` for normalized records and API responses. JSON object insertion order must be preserved for presentation fingerprints.

## Wire capture contract

`model::Capture` fields: `id: String`, `timestamp: i64` (Unix milliseconds), `source: String`, `task_version: Option<String>`, `adapter: Option<String>`, `status: u16`, `duration_ms: f64`, `request: Vec<u8>`, `response: Vec<u8>`, `capture_complete: bool`, `transport_error: Option<String>`, `secret: Option<String>` (forwarded credential, memory only), `local_token: Option<String>` (registered-key client token, memory only), `access_token: Option<String>` (workspace token, memory only). All three known secrets are scrubbed independently if echoed in request or response fields. Redaction matches only original text, preserving longest-first and first-observed priority for ties; inserted markers are never scanned again, so short or repeated credentials cannot amplify the output recursively.

Each privacy pass deduplicates secrets and caps construction at 32,768 patterns and 1 MiB of pattern bytes. More than four secrets use a sparse `LeftmostFirst` Aho-Corasick NFA solely to skip original strings without a match; exact replacement retains the existing priority rules. No overlapping-output enumeration is used. A 64 MiB work allowance charges pattern bytes, string scans, every fragment visit (including markers), and emitted fragments before allocation. All passes in an import share one allowance; each live capture has its own. Imports fail atomically with a typed resource error on exhaustion. Live normalization instead builds a minimal schema-valid record with a fresh UUID-based ID, numeric timestamp/status/latency, redacted source and any transport-error text, no original body content, `capture_complete=false`, and `normalization_error`. The collector counts newly incomplete normalization once and persists neighboring records normally.

The six capture-envelope field names (`request`, `response`, `id`, `source`, `task_version`, and `transport_error`) are generated structure and remain unchanged during privacy filtering. Their values, including original body keys and metadata text, retain the ordinary redaction rules. This prevents a secret that matches an internal field name from corrupting the saved record or rolling back neighboring captures. Definition and grouping-context changes still isolate observations conservatively.

`model::NormalizeOptions`: `provider: Option<String>`, `capture_state: bool`, `redact_keys: Vec<String>`, `input_price_per_million: Option<f64>`, `output_price_per_million: Option<f64>`. `normalize(&Capture, &NormalizeOptions) -> Value`. `sample_records() -> Vec<Value>` creates synthetic records with relative recent timestamps and varied sources/types/versions/errors. `import_records(text: &str, format: &str, options: &NormalizeOptions) -> anyhow::Result<Vec<Value>>`, supporting `observer-jsonl` and an explicitly documented real existing log adapter. Exported records can be reimported using explicit provenance IDs; reject invalid records, do not trust supplied grouping fingerprints. Malformed question definition JSON remains invalid observation evidence and survives export/reimport; imports recompute answer validity and group identities.

Record JSON (all keys present, absent data is null):

```
{schema_version:1,id,event_kind,timestamp,imported_at,timestamp_basis,source,provider,model,requested_model,status,duration_ms,
 input_tokens,output_tokens,cost_usd,cost_basis,source_event_id,import_format,
 capture_complete,state_retained,state,transport_error,sample:false,
 answers:[{key,kind,group_id,definition_id,presentation_id,candidate_id,
   task_version,definition,value,probabilities,confidence,valid,error,warnings,
   family_id,family_name,adapter,instance_ref,mapping_reason,raw_answer,definition_redacted}],
 actions:[],labels:[]}
```

`value` is Choice string / Score number / Noul probability. `kind` is lowercase `choice|score|noul|unknown`. Status errors, transfer failures and invalid/missing answers do not enter valid distributions. A Score discrepancy greater than 0.001 against the weighted displayed probabilities produces a `warnings` entry instead of structural invalidity. Otherwise valid warned answers retain the reported score in distributions; neither original value is rewritten and no cause is inferred. The Laya adapter accepts its string-list Choice criteria and one to 32 Score levels, and uses its documented four-decimal probability rounding bound when checking the total. The offline [model catalog](models.md) extends validation with source-reviewed provider profiles, including rounded distributions, wider rubrics, structured/omitted legends and model-specific Score semantics. Mapped-model confidence may be omitted with a warning; present malformed fields remain invalid. Imported application actions have `event_kind=application_action`, do not enter inference accounting, and retain unknown original timing/transport facts as null with a separately labeled import timestamp. Fingerprints are source/key/definition/presentation/task scoped; a family is separate from strict identity. Native headers are never stored. OpenRouter finite, nonnegative `usage.cost` is recognized as USD with `cost_basis=provider_reported`, ahead of `configured_estimate`; other providers retain unverified `usage.cost` in extension data. Estimates require both explicit USD token rates and known usage. Missing cost stays unknown, while a reported zero remains zero. Sample cost is labeled synthetic.

Observer imports also preserve null event timestamps, assigning an import timestamp when absent or null and setting `timestamp_basis=import`. Token counts must be nonnegative signed 64-bit integers; out-of-range native usage stays unknown and cannot establish estimated cost, while invalid imported counts are rejected. String credentials inside sensitive arrays/objects are collected for redaction of echoes elsewhere in the record. Answer and review keys preserve arbitrary strings, including empty keys. A valid answer requires an explicit supported type in its original question definition; response metadata cannot supply a missing definition type.

## Storage interface

`Store::open_encrypted(path: &Path, key: String, retention_days: u32, max_records: usize) -> Result<Store>` for live history and `open_demo(path, retention_days, max_records)` for demo, cloneable. Unsupported schemas are checked through a read-only connection before plaintext migration or any writer connection opens. Preflight includes committed WAL state and preserves main database/WAL bytes on rejection; SQLite may rebuild the transient SHM index. The writer checks the schema again before schema or journal changes. `is_empty() -> Result<bool>` (indexed existence check), `writer_connection() -> Result<Connection>`, `write_batch(conn: &mut Connection, records: &[Value]) -> Result<usize>`, `dashboard(&Filter) -> Result<Value>`, `request(id: &str) -> Result<Option<Value>>`, `group(id: &str, &Filter) -> Result<Option<Value>>`, `export_page(&Filter, format: &str, after: i64, through: Option<i64>) -> Result<(String,i64,i64,bool)>`, `add_label(id: &str, key: &str, label: &str) -> Result<()>`, `delete_all() -> Result<()>`.

`Filter` (Deserialize + Default): `source, model, window, group, status, search, group_search, request_cursor, group_cursor: Option<String>` plus `from, to: Option<i64>` in Unix milliseconds. `window`: `1h|24h|7d|all`, default `24h`. Explicit `from`/`to` override the preset and are inclusive. Reversed or unsupported date bounds and malformed cursors return HTTP 400. `status=error` includes HTTP statuses at least 400 and any recorded transport error, preserving the original status. Group filters accept a strict group or explicit family ID; an empty group string is equivalent to no group filter.

An internal, non-deserializable `as_of` timestamp freezes each dashboard or export time window. Request and group list cursors affect only their lists; summary totals keep the entire parent scope. `group_search` searches group keys, names, source, kind and identifiers across retained groups, and does not change parent totals. Each list returns up to 100 entries and a nullable next cursor. Request ordering uses descending history timestamp and sequence; group ordering uses descending latest activity and ascending ID. Clients retain their filters when following a cursor and reset cursors after filter changes. Each response has its own snapshot; concurrent collection, deletion, retention and edits can change later pages.

Request details and each export page use a read transaction so parents, answers and labels share a snapshot. Exports fix the maximum sequence and release each page's transaction before download; concurrent retention/deletion and label edits may still change later pages. The server permits one export at a time, and downloads use browser streaming. CSV reads saved parent metrics and the transactionally maintained answer count without reconstructing answer definitions or reviews; JSONL retains complete records. List cursors and group-list search do not narrow exports. Pages target 2 MiB of serialized record data and allow a single larger record up to 32 MiB (including its newline). A fitting record moves to the next page if appending it would exceed that cap; an individually oversized record fails the export. The fixed CSV header is emitted once and is exempt from these data limits, so the maximum first-page size is 32 MiB plus that header.

Dashboard search/group filters select matching parent sequence IDs once into a connection-local temporary table and reuse that selection within the read snapshot. The main database stays read-only; temporary storage uses a 2 MiB pager-cache target and stores only integer IDs. Broad searches scan answer keys once; narrow scopes retain per-parent lookups. Matching a question selects the whole parent request, preserving request-level usage and all its answers. Dense filtered feeds walk the timestamp index, applying the supplied cursor and bounded page lookahead; small or sparse selections retain direct row lookups. The scan heuristic compares selected IDs with retained request count using narrow indexes and favors direct lookups below roughly one-quarter density. It does not estimate timestamp clustering or remaining-page density.

The `request_dashboard` covering index stores scalar metrics, the original event timestamp and transport-error expression alongside filter fields, avoiding repeated reads and JSON parsing of saved bodies. It is created or transactionally rebuilt on opening an existing supported v1 database and maintained by SQLite. A range query establishes timeline bounds; one aggregate request scan computes exact totals, timeline buckets and nearest-rank latency percentiles, plus a snapshot-local map of selected parent IDs to timestamps. Strict groups stream their covering answer index against that map, with compensated means and only one page plus a lookahead retained. Families remain separately aggregated and the final merged list remains bounded to 100. The parent map and percentile buffer scale with selected request count; neither survives the response or caches history across mutations.

## Collector interface

`Collector::start(store: Store, options: NormalizeOptions, capture_limit: usize, capture_slots: usize, queue_capacity: usize) -> Collector`.
Cloneable collector: `reserve_capture() -> Option<OwnedSemaphorePermit>`, `submit(Capture, OwnedSemaphorePermit)` (never awaits), `record_forwarded()`, `record_skipped()`, `health() -> Value`, `async shutdown()`.
One reservation covers at most `capture_limit` bytes of each wire body and remains held until normalization/persistence completes. Capture buffers allocate lazily and grow geometrically, with capacity capped at the per-body limit, so small streaming chunks do not trigger repeated exact-size reallocations. No request waits for a reservation. A missing reservation means capture is skipped and counted; the proxy still forwards the full body. A full queue drops the capture and records the gap. One dedicated writer does normalization and batched writes off the async forwarding runtime. Defaults: 256 KiB per body, 1,024 slots, 1,024 queued events. Graceful shutdown drains; failures are counted independently of SQLite. Health retains a sanitized latest storage diagnostic `{operation,category,at}` without error strings, SQL, record data or paths; it remains historical after recovery and resets with the process.

The writer gathers up to 128 captures or 4 MiB of captured bodies with a 20 ms collection deadline, then splits them by a 4 MiB conservative normalized-JSON work charge before persistence. The charge uses six bytes per UTF-8 byte for escaped strings and keys, conservative scalar/punctuation sizes, and early saturation; it is not a heap-memory limit. Normalization runs once per capture, outside SQLite write transactions. One prepared boundary record may coexist with the preceding subbatch. An individually oversized capture or normalized record runs alone without truncation; single-record normalization, raw queued captures and database caches can still exceed these batch budgets. Each subbatch commits independently: a failed write counts only that subbatch's normalized records as dropped, then later accepted captures can persist after reopening the writer. Order, permits and queue accounting remain held through each record's persistence attempt.

## HTTP and UI API

Proxy: `POST /v1/systemone` to one configured upstream origin/path (default `https://api.typesafe.ai/v1/systemone`). Accept bearer key from caller or `TYPESAFE_API_KEY` in the process environment; fallback requests require `application/json`. Disable redirects and automatic retries; stream full bodies, separately capture bounded copies; accept absent transfer coding or a single `chunked` coding, reject unsupported request transfer codings with 501 before forwarding, and report unsupported upstream transfer codings as 502 with an incomplete capture and transport error; strip hop-by-hop, local cookies and `x-observer-*` headers, and discard upstream `Set-Cookie`. Local metadata headers: `x-observer-source`, `x-observer-task-version`, `x-observer-adapter` (opt-in `jgrep-v1`). Bind loopback only. Upstream configuration is CLI-owned, never a per-request URL; remote URLs require HTTPS and HTTP is limited to loopback endpoints. `--upstream-auth none` is explicitly limited to a loopback model server such as Laya, ignores fallback provider credentials, requires JSON, and still authenticates Observer access through the workspace token as Bearer, `X-Observer-Access`, or dashboard Basic authentication. Authorization and Observer-local headers are removed before forwarding. `--provider` sets the saved adapter identity; TypeSafe and OpenRouter hosts have recognized defaults, and other hosts default to `custom`.

Registered provider keys: `PUT /api/credentials` accepts a provider key and a session/system persistence choice, returns a newly generated local client token once, and rotates any previous token. `GET /api/credentials` returns only configuration status; `DELETE` removes the registered key. The local token is accepted as the SDK's Bearer credential, validated before forwarding, then replaced with the provider key. A token with the reserved local prefix that does not match is rejected without contacting the upstream. System persistence uses OS credential entries scoped to the canonical workspace database path and token hash. On Unix, the path hash uses exact native bytes; valid UTF-8 paths keep their existing hashes, while non-UTF-8 paths use distinct accounts without falling back to ambiguous old lossy-path accounts. Affected workspaces require provider re-registration and leave old entries untouched; canonical aliases still share an account. Non-Unix account naming is unchanged. A new entry is staged before SQLite commits its approval digest; failure to commit leaves the old approved entry intact. Obsolete entries are removed after approval switches. Removing a key or switching to session storage revokes approval before OS cleanup. SQLite stores only the random-token hash, never either secret. Startup can restore approved legacy 0.1.0 workspace entries. After rotation, 0.1.0 cannot read the new layout and a downgrade requires provider re-registration; database backups do not back up the OS keychain. Neither key nor token is written to SQLite or exports, and both are redacted if echoed in captured traffic. System credential operations run off the async HTTP executor. Demo mode cannot configure or forward provider credentials. A loopback upstream with authentication disabled cannot register a provider key, but existing provider credentials can still be removed.

- `GET /api/dashboard` + Filter query -> `{generated_at,sample,sources:[],models:[],summary,timeline,timeline_meta,groups,requests,feed_next_cursor,group_next_cursor,health}`. Server adds live collector health to the Store result. The top-level `sample` flag covers any selected synthetic event, including application-action receipts; inference summary counts remain request-scoped.
- `summary`: `{request_count,action_count,answer_count,error_count,p50_ms,p95_ms,input_tokens,output_tokens,cost_usd,cost_known_requests}`. Unknowns null; known-cost sum is explicitly partial when coverage is incomplete. Summary and group/version detail token totals retain exact signed 64-bit integers while representable. A sum above 9,223,372,036,854,775,807 is null with its `input_tokens_overflow` or `output_tokens_overflow` flag true; otherwise those flags are false. Overflow does not change `input_tokens_known_requests` / `output_tokens_known_requests` coverage counts or other metrics. The UI labels an overflowing total as exceeding range, including the combined token metric when either direction overflows, while retaining coverage denominators. Per-request counts and exports remain unchanged. The browser labels token counts and computed totals beyond its safe-integer range with “About”; direct JSONL/CSV exports retain the exact stored counts.
- `timeline`: `[{timestamp,requests,errors,mean_latency_ms,cost_usd}]`; adaptive buckets cover the entire selected time range, including empty buckets, with a maximum of 168. `timeline_meta={start,end,bucket_width,truncated:false}` uses inclusive start and exclusive end in Unix milliseconds. The final bucket may be partial. Unknown event timestamps are excluded; missing latency/cost remain null. All-history bounds come from selected timed requests, with a recent empty interval when no timed requests exist.
- `groups`: `[{id,name,key,kind,source,definition_id,presentation_id,definition,task_version,family_id,family_name,adapter,answer_count,valid_count,request_count,last_seen,version_count,distribution:[{label,count}],mean_value,mean_confidence}]`. Overview polling reads the shared group statistics; comparison-only metrics are computed on demand by the group-detail endpoint so every poll does not scan saved answer JSON and labels for unused values.
- `requests`: a page of up to 100 summaries `{id,timestamp,source,model,status,failed,transport_error,duration_ms,input_tokens,output_tokens,cost_usd,cost_basis,answer_count,capture_complete,sample}`. Summary and chart counts cover the full selected window, not this page. `feed_next_cursor` and `group_next_cursor` are null on the last page.
- `health`: `{process_id,sample_sequence,forwarded,captured,persisted,dropped,truncated,write_failures,maintenance_failures,maintenance_healthy,last_maintenance_at,queue_depth,queued_bytes,last_persisted_at,last_gap_at,lag_ms,capture_limit,capture_slots,last_error}` (extend as needed). Counters cover the current process. A stable collector `process_id` and increasing `sample_sequence` identify the order of health samples shared by the independent health and dashboard endpoints. `truncated` counts all incomplete captures, including cancellation and unsupported content encoding. Retention failures are reported separately from dropped observations. `last_error` is null or `{operation:open|write|retention,category:database_busy|storage_full|permission_denied|database_unreadable|storage_io|database_error,at:milliseconds}`; it describes the latest failure rather than current health.
- `GET /api/requests/{id}` -> complete normalized record, 404 if absent.
- `GET /api/groups/{id}` + Filter -> `{group,versions:[],timeline:[],timeline_meta,requests:[],answers:[]}`. Answers include `{request_id,timestamp,imported_at,source,key,value,valid,warnings,probabilities,confidence,label}`; unknown event timestamps remain null. Select the latest 100 answers by history time, breaking timestamp ties by newest parent sequence. Bound detail lists and disclose limits. The comparison list keeps the viewed strict version first, then the most recently active versions within the parent scope. Each version has `review_counts={correct,incorrect,unknown,unlabeled}`, warning counts, distribution, latency, usage, known cost and request failure metrics. Parent usage and cost count once per version, but versions can share requests, so version totals are not additive. Every section, including version summaries, retains the caller's parent filter; the detail group further narrows that scope.
- `POST /api/import` JSON `{text,format}` -> `{imported,duplicates}`; queue-independent local import, explicit IDs deduplicate. Limit decoded UTF-8 import text to 8 MiB and 10,000 records; allow JSON escaping overhead within a separately bounded transport body. Imports also enforce 16 MiB per record and 64 MiB per batch for both normalization work and serialized normalized JSON. Work accounting includes a 512-byte minimum per record/answer, 128 bytes per annotation, sanitized input and retained provenance, and metadata repeated for answer grouping or annotation defaults; it is a conservative work budget, not a measurement of heap usage. Check structure before privacy and sanitized replication before answer/annotation construction; bound exact output with counting serialization. Reject the entire import with 413 on a resource limit, distinct from malformed-input 400, without truncating identities or writing partial history. Long metadata is accepted when it fits these budgets. Historical captures are not guaranteed to fit import limits; live capture limits and forwarding behavior are unchanged.
- Stored JSON and Observer JSONL envelopes allow at most 144 nested object/array containers, including the root. This finite allowance accommodates the containers added around raw fields and receipt provenance; it also applies to final imported output. Values above this depth are malformed input (400), with no partial import. Raw provider bodies and System One capture/receipt import envelopes retain the default JSON parser depth guard. Previously retained rows whose added Observer wrappers exceeded that default guard remain readable without a migration; arbitrary deeper rows are not accepted.
- `GET /api/export?format=jsonl|csv` + Filter -> downloadable local records.
- `POST /api/requests/{id}/label` JSON `{key,label}` (`correct|incorrect|unknown`) -> `{ok:true}`.
- `DELETE /api/data` -> `{ok:true}`; UI requires a deliberate confirmation.
- `GET /api/settings` -> public configuration only: `{demo,capture_state,retention_days,max_records,capture_limit,upstream,upstream_auth,provider,version}`. Never expose credentials.

Dashboard assets and local API endpoints require HTTP Basic authentication with username `observer` and a random workspace token held in an owner-only sibling of the database. Append `.token` to the complete database OS path without replacing its extension or converting its filename through lossy Unicode. For example, `team.db` and `team.sqlite` use distinct `team.db.token` and `team.sqlite.token` files. Reuse an existing new-format token under the existing ownership, permission, regular-file and bounded-read checks. When only the legacy extension-replacing `*.access-token` file exists, generate a fresh token and print an upgrade notice; never read or copy the ambiguous legacy secret. Leave the legacy file untouched for rollback, which retains the older executable's same-stem token-sharing limitation. Token-path migration does not alter database keys, history, credential approval state or registered local client tokens.

Registered local client tokens authenticate proxy calls. Direct provider keys require `X-Observer-Access` containing the workspace token; configured provider-key fallback accepts that header or dashboard Basic authentication. A loopback upstream with `--upstream-auth none` accepts the workspace token through Bearer, Basic or `X-Observer-Access` authentication. These workspace-token clients must update their token after a legacy upgrade. Live SQLite databases use SQLCipher with an externally supplied 64-character hexadecimal `JEV_OBSERVER_DB_KEY`; existing plaintext databases migrate before the listener starts. Demo data and explicit JSONL/CSV exports remain plaintext. All local API mutations require `X-Observer-Request: 1`, same-origin validation when Origin is supplied, and allowed Host validation (including reads). Cross-site browser reads identified by Fetch Metadata are rejected. No CORS wildcard. Bound import size. Async HTTP handlers execute SQLite work in `spawn_blocking`.

CLI: `--demo`, `--port` (default 8765), `--db`, `--upstream`, `--upstream-auth bearer|none`, `--provider`, `--capture-state`, `--capture-limit`, `--capture-slots`, `--queue-capacity`, `--retention-days`, `--max-records`, optional explicit input/output rates. Demo uses an isolated database and no provider calls; existing history, including action-only imports, survives restarts without reseeding. Startup uses an existence check rather than aggregating the dashboard. UI build output embedded into the executable, with useful fallback development instructions if unavailable.

## Dashboard behavior

One overview: shared source/model/window/date/search filters; summary strip; volume/latency timeline; question distribution and server-searched recurring groups; paginated request/group lists; live request/failure feed; persistent capture status; request/group detail drawer with version comparison and labels. Pause visible updates while investigating, never ingestion. Poll without overlapping requests, with cancellation and hidden-tab pause. Successful queries count toward a one-second start-to-start cadence, with a minimum 100 ms idle period after slow queries; failures wait one second before retrying. Accessible keyboard/focus behavior, light/dark themes, responsive layout, functional import/export and settings/data controls. Show all unknowns, denominators, cost coverage and incomplete captures honestly. No fake live activity, claims of measured accuracy from confidence, or simulated backend on the production path.

Filter catalogs and the active source/model remain visible during scoped refreshes, failures, and retention changes. Health follows server sample order within a process; a delayed response must not hide a newer reported gap. Request-start ordering distinguishes process transitions and provides a fallback for older responses without sample metadata.

The settings response includes an offline `model_catalog={checked_at,models}`. Each entry records a provider ID, access category, documented model names, proxy/capture integration path, upstream, source URL and normalization profile. This is research metadata; it never queries providers or changes configuration. `POST /api/import` also accepts `format="systemone-capture"` with explicitly identified raw request/response envelopes; see [the capture contract](models.md#library-results-and-custom-apis). Raw captures are normalized and redacted before persistence, and their supplied validity/cost/group claims are ignored.
